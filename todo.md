## 1. Авторизация, изоляция пользователей и хранение данных

### SEC-01 · P0 · Изменение 2FA без авторизации

- [ ] Закрыть неавторизованное чтение и изменение настроек второго фактора.
- **Статус:** воспроизведено для записи настроек и создания секрета; отключение подтверждено по коду.
- **Где:** `api/2fa.ts`, `api/2fa-google.ts`; общий диспетчер `server/index.ts` не добавляет проверку личности перед вызовом этих обработчиков.
- **Проблема:** достаточно передать логин. Можно менять настройки, создавать новый секрет и отключать Google 2FA. `setup` сразу перезаписывает рабочий секрет до подтверждения кода.
- **Последствие:** посторонний может нарушить или ослабить защиту другого аккаунта. Это не означает, что одного логина достаточно для прохождения первого фактора.
- **Сделать:** получать пользователя из серверной сессии; проверять владельца; для замены/отключения требовать повторное подтверждение личности. Хранить новый секрет как ожидающий подтверждения до корректного OTP.
- **Готово, когда:** анонимный и чужой пользователь получают 401/403; неудачная настройка не ломает действующий фактор; разрешённая настройка проходит сквозной тест.

### SEC-02 · P0 · Второй фактор не связан с серверным доступом к данным

- [ ] Перенести завершение MFA в серверный протокол авторизации.
- **Статус:** по коду.
- **Где:** `api/auth-registered-login.ts`, `lib/verifyRegisteredUser.ts`, `src/components/LoginScreen.tsx`.
- **Проблема:** UI выполняет отдельный этап 2FA, но проверка пользователя для защищённых API основывается на логине и пароле, без серверного доказательства завершённого второго фактора.
- **Последствие:** клиентский экран можно обойти прямым обращением к API с первым фактором.
- **Сделать:** после пароля выдавать ограниченный challenge; после MFA — полноценную сессию. Проверять её в защищённых API.
- **Готово, когда:** при включённом MFA одного правильного пароля недостаточно для чтения защищённых данных; challenge нельзя использовать как полноценную сессию.

### SEC-03 · P0 · Справочник компаний доступен для записи без проверки пользователя

- [ ] Защитить чтение компаний и изменение привязок аккаунт–ИНН.
- **Статус:** запись воспроизведена; чтение и использование привязок подтверждены по коду.
- **Где:** `api/companies-save.ts:24`, `api/companies.ts:40`, `api/orders/index.ts`.
- **Проблема:** запись принимает `login` и `customers` без проверки личности и заменяет `account_companies`. Обычное чтение тоже опирается на переданный логин. Эти привязки далее участвуют в ограничении доступных заказов.
- **Последствие:** изменение чужих привязок и нарушение изоляции компаний. Проверка флага `access_all` у указанного логина не доказывает, что запрос сделал его владелец.
- **Сделать:** определять пользователя сервером; разрешённые компании получать из доверенного источника, не назначать произвольные ИНН из клиента. Проверить целостность существующих привязок после исправления.
- **Готово, когда:** нельзя читать или менять чужой список, а обычный пользователь не может добавить произвольную компанию и получить её данные.

### SEC-04 · P0 · Обход фильтра заказов по заказчику

- **Статус:** обход внутри `filterRegisteredOrdersList` воспроизведён изолированным тестом.
- **Где:** `api/orders/index.ts:104–157`, обработчик зарегистрированных пользователей и legacy-кэша.
- **Проблема:** совпадение переданного `inn`/`customerName` возвращается до проверки принадлежности; `serviceMode` доверяется как входному флагу. При отсутствии разрешённых ИНН возможна ветка без ограничения. Legacy-кэш выдаётся до проверки переданного пароля во внешнем источнике, если запись кэша найдена.
- **Последствие:** выдача данных вне разрешённых компаний; для legacy-ветки риск зависит от наличия записи кэша.
- **Сделать:** авторизация до чтения кэша; права service mode — только из серверной роли; запрошенный набор пересекать с разрешённым; пустой набор прав должен означать отсутствие доступа.
- **Готово, когда:** отрицательные тесты закрывают чужой ИНН, имя компании, подставленный serviceMode, отсутствие привязок и неверный пароль при существующем кэше.

## Порядок работ

1. **Граница доступа:** SEC-01–05; отрицательные тесты до исправлений, затем единый серверный протокол сессий (SEC-06). Отдельно проверить доступ каждого чувствительного endpoint по ролям.
2. **Сохранность работы и данных:** SEC-07, API-01–05, API-09, PICK-01–05, PICK-11, UX-01–02.
3. **Надёжность выпуска:** TECH-01–03; проверки на настоящих устройствах и интеграционном стенде.
4. **Удобство и эксплуатация:** оставшиеся P2, начиная со свежести данных, окон маршрута, обновлений и разрешения конфликтов.

## Обязательная ручная проверка после исправлений

Это план верификации, а не список уже доказанных дефектов.

- [ ] Роли: обычный клиент, диспетчер, водитель, администратор; вход по прямой ссылке и прямые API-запросы. Снятие бейджа должно отзывать доступ.
- [ ] Водитель: текущий день, отсутствие рейсов, несколько рейсов, 20 точек, изменение порядка, частичный забор, фото, конфликт изменений диспетчера.
- [ ] Сдача на склад: с заполненной заявкой завершается; без заявки требуется ввод; сервер не позволяет обойти условие.
- [ ] Офлайн: сеть пропала до фото/после фото/после отправки, повтор после timeout, конфликт 409, заполненное хранилище, перезапуск приложения.
- [ ] GPS: первый запуск, отказ разрешения, приблизительная точность, скачок, навигатор поверх приложения, блокировка экрана; устаревшая/подозрительная позиция не выдаётся за текущую точную.
- [ ] Маршруты: произвольный старт, конечный склад, окна, ожидания, ночная смена, ограничения ТС, недоступность/лимит 2ГИС, ручное принятие предложенного порядка.
- [ ] Web/Android/iOS: обновление, скачивание документов, камера, возврат из фонового режима, клавиатура, safe area, поворот и планшет.
- [ ] UI: 320/390/768px и desktop, светлая/тёмная темы, длинные названия/адреса, масштаб текста, клавиатура, screen reader, измерение контраста. Статусы различимы не только цветом.
- [ ] Интеграции: sandbox 1С/2ГИС/уведомлений; отказ, timeout, повтор; отсутствие дублирующих операций и понятная индикация результата.
- [ ] Финансовые операции и документы: отдельная проверка прав, переходов статусов и сверка итоговых сумм на обезличенных бизнес-примерах — выборочного ревью UI недостаточно для утверждения об их полной корректности.
