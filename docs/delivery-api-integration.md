# Заявки и заборная логистика: интеграция с DeliveryWebService

## Реализовано

- `GetZayavki`: обновление `cache_orders` по крону каждые 15 минут. Полный ответ хранится в JSONB, включая `НомерПикапа`, UUID и посылки. Таймаут 45 секунд; ошибочный ответ не стирает предыдущую загрузку. Одновременные запуски исключены блокировкой PostgreSQL.
- «Документы → Заявки»: чтение БД для любого периода. Права зарегистрированных пользователей проверяются сервером; для старых аккаунтов сначала проверяются доступные компании через 1С с их учётными данными. Данные чужих компаний не выдаются по клиентскому флагу `serviceMode`.
- Создание заявки: кнопка формы вызывает `PostZayavka2`. Нужны проверенные ПВЗ и постоянный номер заявки клиента до 50 символов. Клиентский ИНН заменяется разрешённым сервером ИНН заказчика. Подготовленный JSON с выделенными ИД отправлений сохраняется до сетевого запроса. Подтверждённый ответ сохраняет `Номер` и `Ссылка`; повтор использует сохранённую квитанцию. Неизвестный результат не отправляется повторно автоматически.
- До следующей загрузки созданная заявка видна из локальной записи с отметкой «Создана в 1С». Она не предлагается как удаляемый локальный черновик.
- Завершение забора: сохранение номера заявки и запись очереди передачи номера забора выполняются атомарно. Триггер также отслеживает исправления номера и ставит существующие сданные заборы в очередь при миграции.
- `SetPickupNumber`: защищённый cron `/api/cron/sync-pickup-numbers` каждые 5 минут. Проверяются ИНН и однозначность номера заявки; передаётся номер документа 1С. До 20 строк за запуск, до 3 параллельных вызовов; повтор с задержкой при ошибках. Поколение записи защищает от подтверждения устаревшей задачи. Кэш заявок старше 30 минут блокирует передачу до обновления.
- Журнал счетов: выбор строк, дата, заказчик, места, вес, объём, платный вес, номера забора/перевозки/заявки, редактируемая сумма, статус и ошибки. Автоматический расчёт использует `Mest`, `W`, `Value`, `PW` перевозки, тарифы калькулятора и расстояние из карточки либо расчёт по координатам. Для ручного режима сумма первоначально пустая.
- Связь с перевозкой: по `НомерПикапа` (также поддерживается `PickupNumber`) или явно указанному номеру перевозки, обязательно с ИНН заказчика. Конфликтующие и неоднозначные связи блокируются. Для `SetPickupCost` передаётся исходный номер, включая ведущие нули.
- Отправка стоимости: отдельно по каждой выбранной строке, с итоговым количеством успешных передач и номерами ошибок. Проверяется версия строки и актуальность грузовых параметров перед отправкой. Повтор после неизвестного результата блокируется. Изменения сумм, отправки и ручные подтверждения записываются в историю.

## Значение статусов

Диспетчер проверяет суммы и подтверждает передачу выбранных строк. Сервер требует подтверждение передачи; состояние `transmitted` означает **«Передано в 1С»**. По подтверждённому владельцем процесса сценарию счета далее автоматически выставляет 1С. Дополнительное подтверждение выставления для успешных передач не требуется.

Подтверждённый отказ получает статус **«Не передано в 1С — требуется ручное выставление»**. После ручного выставления диспетчер может отметить «Выставлен».

Обрыв связи сохраняет отдельный статус «Передача в 1С не подтверждена — требуется сверка»: перед ручным выставлением нужно проверить результат в 1С, поскольку запрос мог быть принят. Автоматического повтора нет. Зависшее состояние «Отправляется» допускает подтверждение ручного выставления спустя 5 минут.

## Миграция и запуск

1. До выкладки сервера применить `migrations/114_pickup_1c_integration.sql`; для защиты создания заявок также требуется существующая миграция `112_one_c_submissions.sql`.
2. Миграция 114 создаёт `pickup_number_sync`, `pickup_billing`, `pickup_billing_events`, `documents_order_prepared`, триггер очереди и индексы поиска перевозок. Она повторно применима.
3. Деплоить код API и фронтенда.
4. На **выделенном cron VPS** применить изменения из `deploy/crontab.haulz-cron.example`. Не устанавливать второй такой же cron на API VPS/Vercel.
5. Сначала запустить защищённый `refresh-orders-cache`, затем `sync-pickup-numbers` и проверить результаты.
6. Используются существующие серверные учётные данные 1С и `CRON_SECRET`. Для другого контура setter-методов можно задать `ONE_C_DELIVERY_BASE_URL` (до имени метода). Секреты не передаются в браузер.

Обычное обновление заявок охватывает последние 90 дней. Старые уже загруженные записи сохраняются. Первичную историческую загрузку можно выполнять через тот же защищённый cron с `dateFrom=YYYY-MM-DD&dateTo=YYYY-MM-DD`, порциями не более 90 дней. Без такой загрузки исторические заявки до текущего окна не появятся в БД.

## Что подтверждено и что остаётся проверить на контуре

- Локальные проверки используют PGlite и тестовые ответы, без обращений к рабочей 1С и без выставления реальных счетов.
- Проверены атомарная очередь сдачи на склад, повторное применение миграции, передача исходных номеров, межклиентские коллизии, сохранение всех полей перевозки в нормализованной БД, ручная сумма, изменение параметров перед отправкой, частичный успех, права водителя и повторы после неизвестного результата.
- Проверка рабочего `GetPerevozki` отложена по решению пользователя. Фактическое имя нового поля номера забора пока не подтверждено: его контракт не приложен. Требуется обезличенный пример или проверка на согласованном тестовом контуре. Полный JSON ответа уже сохраняется независимо от наличия новых полей; добавлять отдельную обязательную колонку для каждого поля не нужно.
- Нужна проверка бизнес-смысла `PW` и связки «один забор → одна перевозка». Несколько перевозок на один забор сейчас требуют сверки, автоматического распределения одной стоимости между ними нет.
- Миграция и cron подготовлены в репозитории, на рабочей БД/сервере в этой задаче не запускались.
