Ручная проверка новых очередей (на cron-VPS):

```bash
/opt/haulz/cron-call.sh '/api/cron/refresh-cache?kind=invoices&lane=recent'
/opt/haulz/cron-call.sh '/api/cron/refresh-cache?kind=perevozki&lane=active'
tail -n 20 /var/log/haulz-cron-call.log
```
Ответ skipped/not_due_or_running допустим, если задание уже запускалось. Это не подтверждение новой загрузки. Проверять завершённые результаты и ошибки.

Для фронтенда проверить успешное развёртывание после push. Git push сам по себе не подтверждает публикацию сайта. Суммы и статусы проверяются только после обновления обеих частей.

Локальная проверка: 80 тестов; TypeScript фронтенда и бэкенда; production-сборка; проверка установщика cron с сохранением посторонних заданий.

### Коррекция после серверной диагностики

8 400 неизвестных перевозок занимают 353 даты. Их отдельная очередь archive обходит по шесть дат за ночь (00:18–05:18); полный обход при неизменном наборе и без ошибок — около 59 ночей. Это намеренно медленная проверка старых данных, не обещание актуальности архива. Записи не удаляются и не считаются завершёнными. Неизвестные перевозки последних 90 дней и известные незавершённые любого возраста остаются в active. При появлении известного незавершённого статуса архивная запись автоматически попадает в active. Ошибка не продвигает курсор. Дополнительных миграций нет; установщик теперь устанавливает восемь заданий refresh-cache.

Точную новую длительность active определять повторным check-document-refresh.ts: даты разных групп могут пересекаться, а закрытые дни на семидневном контроле добавляют работу.
