# Снижение нагрузки на 1С

## Расписание (Москва)

Использовать deploy/crontab.haulz-cron.example только на cron-VPS.
Изменение crontab без обновления API не меняет период данных.

| Метод | Запуск | Данные |
|---|---|---|
| refresh-cache | проверка */5, работа раз в 25 минут по БД | 3 дня; перевозки → отправки → счета → акты → заказчики |
| refresh-cache-deep | 02:00 | 10 дней; четыре типа последовательно |
| refresh-orders-cache | каждый час :00 | сегодня и два предыдущих дня, три отдельных запроса |
| refresh-orders-cache?mode=backfill | 01:30 | один день истории, сохранённый курсор |
| backfill-sendings-metrics | 03:30 | один день истории по умолчанию |
| refresh-suppliers-cache | 03:00 | справочник |
| refresh-tariffs-cache | 04:00 | тарифы |
| refresh-sverki-cache | 00:00 | акты сверок |
| refresh-dogovors-cache | 05:00 | договоры |
| refresh-pvz-cache | 06:00 | ПВЗ |
| process-claim-push-queue | каждый час :07 | очередь уведомлений |
| notification-poll | каждый час :00 | БД: 25 дней, только записи обновлённые за 3 часа |
| notification-daily-summary | 13:17 | сводка из БД |
| weekly-partner-summary | 07:00 | проверка настроенной периодичности |
| weekly-partner-summary?continue=1 | каждые 5 минут с 07:05 до 07:55 | только продолжение активной рассылки |
| sync-pickup-numbers | каждый час :20 | очередь номеров для 1С |

Один тип документов обновляется примерно раз в 125 минут. Ошибка не переключает тип.
Пропущенные запуски и ошибки увеличивают интервал. */25 не используется: даёт 25/25/10 минут.
Очередь и курсоры переживают перезапуск. Повторы recent/orders: 5, 10, затем 60 минут и далее до 6 часов; фактический повтор происходит на следующем тике cron.

История заявок начинается с ORDERS_BACKFILL_FROM (по умолчанию 1 января текущего года).
Конечный день фиксируется при первой успешной порции: день перед текущим трёхдневным окном.
После завершения обращения к 1С для этой истории прекращаются. При одном дне за ночь большая история заполняется медленно; ручная порция допускает до трёх дней.
Для метрик проверить SENDINGS_BACKFILL_CHUNK_DAYS=1 и SENDINGS_BACKFILL_MAX_CHUNKS_PER_RUN=1: старое окружение может переопределять код.

## Общий ограничитель

VPS-процессы используют общую БД. Для fetch к tdn.postb.ru/workbase/hs/ разрешён один запрос одновременно, включая чтение тела ответа, с паузой 2 секунды.
Пользовательские запросы имеют приоритет над фоновыми. После сбоя процесса блокировка освобождается по сроку.
После трёх ошибок сети/HTTP 429/5xx фон приостанавливается на 15 минут.
Ограничитель установлен в server/index.ts: отдельные скрипты и serverless-обработчики вне этого сервера им не охвачены.
Пользовательские операции записи в 1С автоматически не повторяются.

notification-poll больше не получает перевозки, счета или детали последней мили из 1С.
Неполные данные ждут обновления БД. Записи старше 10 дней не обновляются регулярными окнами; изменения таких документов могут не попасть в уведомления. Для них нужна отдельная сверка истории либо API изменений со стороны 1С.

## Установка

1. Сохранить crontab: `crontab -l > /root/crontab-before-load-control.txt`.
2. Обновить код API и cron VPS через `git fetch` и `git merge --ff-only`. При конфликте остановиться.
3. Применить миграцию к общей БД один раз, до перезапуска:

```bash
cd /opt/haulz/app
(
  set -a
  source /opt/haulz/.env
  set +a
  psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f migrations/116_cron_load_control.sql
)
```

Миграция повторяемая, данные не удаляет. Для диагностики заявок также нужна миграция 115.
Оба процесса должны использовать ту же БД.

4. Проверить часовой пояс ОС cron-VPS: `timedatectl`. Нужен Europe/Moscow. Переменная TZ в crontab задаёт окружение команд, но не гарантирует часовой пояс демона cron.
5. Проверить лимит cron-сервиса HAULZ_REQUEST_TIMEOUT_MS=300000. Обновить /opt/haulz/cron-call.sh из deploy/cron-call.sh.
6. Перезапустить haulz-api на API-VPS и haulz-cron на cron-VPS.
7. Проверить health с повторами; внести строки примера в `crontab -e`, сохранив сторонние задания.

```bash
curl -fsS --retry 10 --retry-connrefused --retry-delay 2 --max-time 5 http://127.0.0.1:3000/health
```

## Проверка

- Два вызова refresh-cache подряд: второй skipped/not_due_or_running.
- refresh-orders-cache: results содержит три однодневных окна, диагностика complete.
- Курсор documents_recent в cron_work_state переходит между пятью типами без пропусков.
- При ошибке 1С сохраняется прежний кэш, курсор не продвигается.
- one_c_request_gate имеет одного владельца; истёкшая блокировка восстанавливается.
- notification-poll не вызывает 1С; изоляция заказчиков сохраняется.
- Уменьшение окна не удаляет старые документы из БД.
- После обхода истории backfill возвращает done.

## Ограничения

API изменений после даты/курсора должен предоставить разработчик 1С.
Транзакционная замена всех справочников и полное устранение запросов исторического backfill метрик этой правкой не реализованы.
Совпадения запусков возможны, включая 13:17 после задержек. Очередь предотвращает параллельные обращения к 1С, но не гарантирует время окончания.
