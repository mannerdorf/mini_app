# Диспетчеризация заборной логистики

## Границы модуля

Новые экраны находятся в `src/features/pickup`, сервер — в `api/pickup/index.ts`, общий контракт — в `lib/pickup/model.ts`.
Модуль работает со своими таблицами `pickup_*`. Справочники `cache_customers`, `cache_suppliers` и зарегистрированных пользователей читаются; запись в 1С не выполняется.
В существующем приложении добавлены только права `dispatcher` / `driver`, кнопки меню и ленивое подключение экранов профиля.

## Включение

1. Установить зависимости через `npm ci`. PGlite используется только как devDependency для тестов.
2. Применить миграцию к базе приложения штатным способом:

   ```sh
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/104_pickup_dispatch.sql
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/105_pickup_jobs_search_columns.sql
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/106_pickup_job_cancelled.sql
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/107_pickup_supplier_contacts.sql
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/108_pickup_driver_locations.sql
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/109_pickup_gps_quality.sql
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/110_pickup_job_number.sql
   ```

   Миграция 104 создаёт таблицы `pickup_*`; 105 добавляет индексируемые колонки номера заявки, перевозки и ИНН; 110 — сквозной **номер забора** `job_number` (формат `ZB-000001`, отдельно от заявки и перевозки) (полный JSON задания по-прежнему в `pickup_jobs.data`); 106 добавляет статус `cancelled` для отмены заборов; 107 — справочник контактных лиц по ИНН отправителя (`pickup_supplier_contacts`, заполняется при сохранении забора). Повторное применение допустимо.
3. Собрать и развернуть фронтенд и API существующим процессом. VPS автоматически обнаруживает `/api/pickup` по `api/pickup/index.ts`.
4. В Админка → Пользователи включить бейдж «Диспетчер» соответствующему пользователю, «Водитель» — водителям. Не требуется давать доступ к CMS или общий бейдж HAULZ водителю.
5. В Админка → Пользователи включить бейдж «Диспетчер» или «Водитель». Диспетчер в приложении может удалить маршрут в любом статусе, включая выполняемый, без дополнительных CMS-прав. Заборы остаются в журнале дня без `route_id` с прежними статусами; фото и история сохраняются. Удалённый маршрут исчезает у водителя. В CMS отдельное действие суперадминистратора по-прежнему предназначено для завершённых маршрутов.
6. Профиль → HAULZ → Диспетчеризация: для каждого города добавить реальный склад с адресом и часами приёмки, автомобили и водителей. Водитель связывается с существующим активным аккаунтом с бейджем «Водитель». В справочниках водителей и автомобилей можно **удалить** запись: если ресурс не участвовал в маршрутах — строка удаляется; если уже был в истории маршрутов — запись уходит в архив (`active=false`) и скрывается из списка. Удаление блокируется, пока ресурс на незавершённом маршруте.
7. Создать заборы вручную, выбрать заказчика и отправителя из справочников, создать маршрут и распределить заборы. Вкладка **«Выставление счетов»** — таблица заборов за выбранный день со статусом «Сдан на склад» и заполненным номером перевозки.
8. Опубликовать маршрут. Водитель открывает Профиль → HAULZ → Водители — мой маршрут.

## Правила

- Москва и Калининград имеют отдельные дневные планы. Дата по умолчанию и время истории учитывают часовой пояс города. Ожидаемая нагрузка — до 20 точек/город/день; искусственного запрета на 21-ю заявку нет.
- Несколько рейсов одного водителя допускаются. Начать второй рейс до завершения первого нельзя; то же ограничение действует для машины.
- Заказчик и отправитель проверяются сервером по ИНН; названия сохраняются из справочников.
- Контакты на точке при сохранении забора дописываются в справочник контактных лиц этого отправителя (уникальность по нормализованному телефону). В форме забора можно подставить контакт из справочника после выбора отправителя.
- Окно забора обязательно. График недели склада, инструкции, требования и пропуска пока хранятся текстом. Время в пути, пробки, праздничные дни и грузовые ограничения автоматически не рассчитываются.
- Вес и объём могут быть неизвестны: это явно показывается предупреждением. Известное превышение вместимости **не блокирует публикацию** — только предупреждение в окне проверки; добавление точки в уже опубликованный маршрут по-прежнему может быть отклонено сервером при перегрузе.
- При создании забору присваивается **уникальный номер** `job_number` (`ZB-000001` …) — сквозной ключ для UI, БД и будущей связки с 1С. Это **не** номер заявки и **не** номер перевозки; «Серия по графику» — только метка периодического графика.
- Номер заявки вносится на складе после забора (и позже подтягивается из 1С по крону). Номер перевозки и платный вес появляются после сплита/приёмки — для расчёта заборной логистики и журнала выставления счетов.
- Номер перевозки необязателен до его появления. Документы-основания (несколько счетов отправителя) отделены от цены заказчику.
- Водитель получает только собственные опубликованные маршруты и не получает поля стоимости/оплаты/тарифного километража через API. Фото и действия также проверяют назначение маршрута и текущие права.
- Диспетчер может **удалить** забор в статусе «Ожидает забора» или «Отменён» (кнопка «Удалить», с подтверждением). Начатые заборы удалять нельзя — только отмена с причиной. Пользователи с полным служебным доступом (CMS + служебный режим + аналитика + HAULZ) могут **удалить завершённые** заборы (груз забран, частичный, сдан на склад, закрыто диспетчером) — вместе с фото; заборы «на точке» и «проблема» по-прежнему только через отмену/решение.
- Диспетчер может **вручную изменить статус** забора на маршруте (опубликован / выполняется / завершён), если у водителя не работает приложение: API `set_job_status`, обязательный комментарий; для «груз забран» / «частичный» — фактическое число мест **без требования фото**.
- Диспетчер может **редактировать** заборы в статусе «Ожидает забора» — в том числе уже добавленные в маршрут (кнопка «Изменить»). После сохранения версия маршрута растёт; водитель подтверждает ознакомление. Начатые/выполненные точки не редактируются. Смена даты/города — через «Снять с маршрута». Изменение состава/порядка повышает версию маршрута; водитель подтверждает ознакомление.
- Успешный забор требует положительного целого фактического количества мест и 1–3 фото. Фотографии сжимаются на устройстве до JPEG, максимум 900 КБ на фото на сервере. Они хранятся в закрытой таблице Postgres и выдаются после проверки доступа.
- Любое расхождение количества требует комментария и решения диспетчера. При нуле водитель использует «Проблема / не забрал».
- «Сдал на склад» подтверждает водитель. Отдельное подтверждение кладовщиком не добавлено, так как правило ещё не согласовано. Частичные заборы и проблемы должны иметь решение диспетчера до закрытия маршрута.
- Повтор отправленного действия с тем же requestId не создаёт дубликатов. Версии строк защищают от перезаписи устаревших данных. Изменения и результаты записываются в журнал.
- Диспетчер опрашивает API каждые 15 секунд, водитель — каждые 30 секунд. Передача GPS описана ниже; фоновые push-уведомления не включены.

## Ограниченный офлайн-режим

После успешной загрузки водитель может открыть сохранённую копию дня. Не доставленная из-за сетевого сбоя отметка вместе с фото сохраняется в IndexedDB этого пользователя. Пароли в кэш модуля не записываются.
Пользователь видит очередь и явно отправляет её кнопкой «Отправить отметки». До синхронизации очереди следующие действия по тому же маршруту блокируются, чтобы не нарушить порядок событий. При конфликте сохраняются локальная отметка и сообщение об ошибке; не применяется скрытая перезапись серверных данных.
Это не полное автономное выполнение всего рейса. Необходимо синхронизировать отметки до выхода из аккаунта/очистки данных приложения. Серверная проверка отозванных прав выполняется при подключении.

## Карта и навигация

Точки с вручную указанными координатами показываются на карте. Для всех адресов доступны ссылки на внешнюю навигацию до точки и склада. Ссылки на схемы проезда принимают только HTTP(S).
Автоматическое геокодирование, ETA и оптимизация последовательности не подключены: нет согласованного провайдера и ключей. Распределение и порядок задаёт диспетчер. Не выводятся вымышленные времена прибытия.

## Проверки

`npm run test:pickup` проверяет валидацию и реальные SQL-запросы API на PostgreSQL WASM (PGlite): миграцию, права и изоляцию водителей, скрытие финансов, фото, повтор запросов, расхождения, сдачу на склад, ограничения загрузки, версии и подтверждение изменений.
Для проверки сетевых блокировок между несколькими серверными процессами дополнительно нужен staging с обычным PostgreSQL.

Ручной smoke: создать/назначить/опубликовать маршрут → войти водителем → начать → указать места и фото → выполнить точки → сдать на склад. Проверить мобильную ширину и вход пользователя без новых прав.

## Согласование перед расширением

Отдельно согласовать обязательность доверенностей и файлов счетов, распределение мест по каждому счёту, подтверждение кладовщика, исходную точку выезда, стоимость наёмного перевозчика, геокодер/оптимизатор и срок хранения фото/локальных копий.
Парсер сообщений диспетчера, справочник повторных адресов отправителей и объединение нескольких заявок в одну остановку не включены в эту версию: каждый забор — отдельная позиция маршрута.

## План дня и справочники

Стартовый экран диспетчера — «План дня». Карточки счётчиков служат фильтрами; поиск учитывает адрес, заказчика, отправителя, номера заявки/перевозки, маршрут и водителя. Отменённые заборы доступны отдельным фильтром и не входят в активные счётчики. Заборы с согласованным расхождением исключаются из «Требуют решения».

Подробности открываются в боковой карточке (на телефоне — на весь экран). Закрытие возвращает к текущему списку; Escape также закрывает карточку. При редактировании открывается существующая форма.

«Справочники» дают отдельный вход к водителям и автомобилям, с поиском по реквизитам. Цветовые акценты плана: синий — обзор, янтарный — не распределено, зелёный — груз забран, красный — требуется решение. Состояния всегда подписаны текстом. Стили ограничены модулем pickup.

### Массовое назначение и форма

В плане дня можно выделить несколько неназначенных заборов (или все подходящие под текущий поиск) и выбрать маршрут. До подтверждения отображаются суммарные места, вес, объём и вместимость. Назначение выполняется одним запросом `assign_many` внутри транзакции: при устаревшей версии, несовпадении города/даты, неподходящем окне или превышении вместимости не назначается ни одна заявка. Повтор того же запроса не создаёт повторных изменений. Для массового назначения доступны черновики и опубликованные маршруты до начала выполнения.

Форма разделена на четыре сворачиваемых блока: заказчик/отправитель, адрес/время, груз, стоимость/документы. Повторный график и дополнительные сведения раскрываются по необходимости. Кнопки сохранения закреплены внизу, при ошибке обязательного поля его блок автоматически раскрывается.

Черновики новых заявок и копий сохраняются в sessionStorage текущей вкладки отдельно для пользователя, города и исходной даты. Они восстанавливаются после закрытия формы и очищаются после успешного сохранения. Кнопка «Начать заново» очищает ввод после подтверждения. Данные редактируемых существующих заявок автоматически не восстанавливаются во избежание использования устаревших версий. Черновик не отправляется на сервер, не содержит пароль и исчезает при закрытии вкладки.

### Оперативная работа диспетчера

- «Внимание» объединяет нерешённые проблемы/расхождения, окна, до окончания которых осталось не более 30 минут, уже закрывшиеся окна и неподтверждённые версии маршрутов. Часы учитывают город, будущие даты не получают предупреждений о закрытии. Это контроль окон, не прогноз опоздания с учётом дороги.
- Из события можно позвонить контакту, открыть данные забора/маршрут, создать повторный забор или зафиксировать решение. При повторе диспетчер отдельно проверяет дату и оставшиеся места; запись решения сама по себе не создаёт новую заявку.
- Публикация проходит через сводку с водителем, машиной, грузом, последовательностью адресов и конечным складом. Очевидные ограничения блокируют подтверждение; сервер повторяет проверки.
- Точки можно перетаскивать за ручку либо перемещать кнопками. Начатые и выполненные позиции фиксируются; при изменении версии маршрута во время перетаскивания операция отклоняется.
- Удаление заявок и маршрутов доступно по красной иконке корзины с подсказкой и подтверждением. Доступность ресурса отделена от его рейсов на выбранную дату; это не глобальная проверка занятости во всех городах/днях.
- В новой заявке доступны адреса, контакты, часы и инструкции предыдущих заборов выбранного отправителя в этом городе. Подстановка выполняется явно; цену и счета не копирует. Контакты и график нужно проверить на актуальность.

### Экран водителя

- В первую очередь открывается выполняемый рейс, затем опубликованный. День/город вынесены в сворачиваемые настройки; единственный рейс не дублируется в боковом списке.
- Подсказка показывает текущую точку, ожидание синхронизации/решения, переход к складу или завершение. Прогресс закрытых точек отделён от количества фактических заборов.
- Текущая точка раскрыта, остальные свёрнуты. Доступны навигация, контакты, инструкции, документы и груз. Цена заказчика по-прежнему не приходит в API водителя.
- Перед стартом водитель проверяет маршрут; при изменениях в пути подтверждает новую версию. До подтверждения действия по точкам недоступны.
- Забор подтверждается в отдельном блоке: фактическое количество, фото и объяснение расхождения. Кнопка «По плану» заполняет количество только по нажатию. Ввод не сбрасывается при отметке прибытия/обновлении версии точки в открытом экране.
- «Не удалось забрать» открывает отдельную форму с типовыми причинами и свободным комментарием. Фото и положительное количество для сообщения о проблеме не требуются.
- Сдача на склад доступна после обработки точек и решений по проблемам. Отметки без связи явно остаются в очереди устройства до отправки; полноценный офлайн-рейс не добавлен.


### Монитор рейсов и GPS

- Вкладка «Монитор рейсов» показывает водителей и машины выбранного города/дня, статус маршрута и «Груз забран: 9 из 10». Частичные заборы входят в число точек с полученным грузом и подписаны отдельно. Отменённые исключены, закрытые без забора не увеличивают счётчик.
- Карта показывает последнюю позицию выбранного водителя, время фиксации и точность. Свежая позиция обозначена синим; при возрасте более 7 минут она помечается устаревшей (5 минут между обновлениями и 2 минуты запаса). Последняя позиция завершённого рейса не обозначается текущей. «На точке» означает отметку водителя, «Следующий забор» — плановый адрес, не GPS.
- Водитель начинает маршрут и сам нажимает «Передавать моё местоположение», затем разрешает геолокацию. HTTPS (или localhost) обязателен; WebView/браузер должен разрешать Geolocation API. Каждые 5 минут запрашивается новый fix, пока экран видим. При скрытии экрана передача приостанавливается; после закрытия раздела, смены выбранного рейса, выхода из аккаунта, завершения или отключения GPS прекращается. При повторном входе нужно включить заново. Уже отправленный запрос может завершиться после отключения.
- Это передача из открытого интерфейса. Непрерывная работа при заблокированном телефоне/закрытом приложении потребует отдельной нативной фоновой службы и в эту реализацию не входит. Проверять разрешение устройства следует на целевых Android/iOS/WebView.
- Миграция 108 добавляет только `pickup_driver_locations`: одну последнюю позицию на рейс, без истории движения. При удалении маршрута запись удаляется каскадно. Последняя позиция остаётся в БД и после завершения/выключения; автоматический срок удаления не задан.
- Сервер принимает координаты только от активного назначенного водителя начатого рейса, включая проверку для аккаунта с обоими бейджами. Координаты должны быть конечными числами в допустимом диапазоне; fix не старше 2 минут и не более 30 секунд в будущем. Старые/повторные fix не заменяют более свежие и не освежают время получения. Версии маршрутов и подтверждения GPS не меняет.
- GPS не попадает в очередь офлайн-действий; в БД не накапливаются квитанции на каждый fix. Запись блокирует только свой маршрут. При отсутствии миграции обычная диспетчеризация продолжает работать, GPS показывает состояние «ещё не подключён».

### Изменение порядка водителем

В опубликованном или выполняемом своём маршруте водитель открывает «Изменить порядок точек». Компактный список поддерживает перетаскивание за ручку мышью/пальцем с прокруткой у края, стрелки и клавиатуру. Нажатие «Сохранить порядок» отправляет изменения диспетчеру; «Отмена» ничего не меняет. Начатые/выполненные позиции закреплены, перенос через них запрещён; склад всегда последний.

Изменение фиксируется событием «Водитель изменил порядок точек». Новая версия собственного выполняемого маршрута считается просмотренной водителем. Если до изменения поступила новая версия от диспетчера, её нужно сначала подтвердить. Устаревшее сохранение отклоняется, чужие маршруты и завершённые рейсы недоступны. Перестановка требует связи и не ставится в офлайн-очередь.

### Проверка заявки при сдаче на склад

При нажатии водителем «Сдал на склад» проверяется поле `zayavkaNumber` («Заявка», номер заявки) каждого фактически забранного груза, включая частичные заборы. Если номера уже заполнены, остаётся обычное подтверждение сдачи. Если номера отсутствуют, форма показывает отправителя/адрес каждого такого забора и обязательное поле номера. Пустые значения и пробелы не принимаются; до заполнения всех номеров завершение недоступно. Отменённые заборы и закрытые диспетчером без груза (`resolved`) номера не требуют.

Новые номера передаются в `deposit.zayavka_numbers` как `{id, version, number}`. Сервер проверяет доступ к маршруту, версии заборов, принадлежность переданных ID и отсутствие ранее заполненного номера. Сохранение номеров, индексируемой колонки `zayavka_number`, истории и сдачи на склад выполняется одной транзакцией. Водитель не может этим действием заменить заполненный номер или изменить другие поля. Повтор запроса идемпотентен. Существующие правила готовности груза/решения расхождений сохранены; наличие номера не заменяет их. Проверяется заполнение поля, без создания или проверки документа в 1С. Новая миграция для этой проверки не нужна.

### Проверка достоверности GPS

Миграция `109_pickup_gps_quality.sql` добавляет время последнего проверенного сообщения и предупреждение; её необходимо применить после 108. Без 109 приём новых координат возвращает 503, остальные операции доступны.

- Проверка на сервере под блокировкой маршрута: расстояние по прямой, запас 500 м, погрешности ограничены 200 м с каждой стороны, порог скорости 180 км/ч. 100 км за 5 минут отклоняются.
- Подозрительная позиция не заменяет предыдущие координаты, их точность и время. Сохраняется предупреждение «GPS ненадёжен». Повторные сообщения со старым временем не снимают предупреждение. После скачка допустимое расстояние ограничено бюджетом 5 минут, чтобы ожидание не легализовало подмену.
- Погрешность >1000 м отклоняется при наличии предыдущей позиции. Первая такая позиция показывается только как ненадёжная приблизительная область. Погрешность >200 м отображается полупрозрачным кругом на OpenStreetMap без маркера, не используется для расчёта.
- Возврат допустимой позиции снимает предупреждение. При реальном дальнем перемещении после срабатывания фильтра может потребоваться ориентир по остановке; автоматический сброс доверия не предусмотрен.
- `usableRoutingLocation` исключает подозрительные, приблизительные и устаревшие (>7 минут) координаты. `routingOrigin` выбирает адрес последней остановки по событию водителя (прибытие/забор/проблема) и явно помечает его ориентиром. При отсутствии события начало выбирается вручную. В модуле пока нет автоматического пересчёта через 2ГИС; его подключение должно использовать этот фильтр.
- Это эвристика, не доказательство подлинности GPS. Первая точная позиция и плавная подмена могут пройти проверку. Точность устройства в метрах — оценка: https://developer.mozilla.org/en-US/docs/Web/API/GeolocationCoordinates/accuracy .

### Проверка и улучшение маршрута (до 20 точек)

В карточке диспетчера кнопка «Проверить маршрут» открывает оценку текущего порядка, предложение и сравнение на карте. Применение выполняется только кнопкой «Применить порядок» через существующую операцию `reorder`. Проверка не меняет данные.

- Серверная операция `check_route` доступна только диспетчеру. Снимок читается в короткой READ ONLY транзакции; соединение освобождается до сетевых запросов. Параметры в запросе: id, version, необязательный startAddress и windowsConfirmed. Ключ берётся только из серверного окружения HAULZ_DGIS_API_KEY / DGIS_API_KEY. Значение ключа не включается в ошибки или ответы клиенту. Локальный .env для разработки этого изменения не читается.
- Отдельный адаптер `routeProvider.ts` использует облачный Routing API 2ГИС с transport=truck и params.truck (масса в тоннах, габариты в метрах, опасность груза, числовые ID пропусков). Легкового обходного расчёта нет. Недостаточные параметры и ошибки доступа дают серую оценку. Флаг игнорирования пропусков / неподтверждённые грузовые ограничения также дают замечание.
- Дополнительные поля автомобиля сохраняются в существующем JSON data, отдельная миграция для проверки маршрутов не нужна. Полная масса с грузом задаётся для максимальной загрузки рейса; перед расчётом её следует актуализировать. Это консервативный расчёт с одной массой на все участки.
- Старт плана — склад HAULZ в start_time, либо явно заданный адрес. Для выполняемого рейса: свежее надёжное GPS → последняя отмеченная водителем остановка как явно обозначенный ориентир → ручной адрес. Расчёт оценивает оставшиеся pending/arrived; начатые/выполненные позиции при применении остаются фиксированными. Незакрытые проблемы сначала требуют решения.
- Матрица направленная: путь А→Б может отличаться от Б→А. Пары направляются пачками до 25, до 3 запросов одновременно; суммарный таймаут 85 секунд, клиентский 100 секунд. Для api/pickup/index.ts в vercel.json задан maxDuration=120; на другом хосте API нужно разрешить такой срок выполнения. До 20 точек — до 421 пары и до двух итоговых маршрутов для геометрии; 2ГИС тарифицирует пары отдельно. Одинаковые точки дают нулевой переход. Повторный результат переиспользуется до 5 минут в пределах экземпляра сервера; не более двух проверок в минуту на диспетчера.
- Для близкого старта используются текущие пробки jam, для будущего — statistics с UTC даты/времени города (Москва +03, Калининград +02). Все участки оцениваются по обстановке на время старта; изменение пробок в течение рейса не прогнозируется отдельно на каждом участке.
- Лексикографический приоритет: доступность проезда → число опозданий на забор → минуты этих опозданий → склад/смена → длительность → километры. Поиск: обмены и развороты последовательности незапущенных точек, максимум 12 проходов. Это ограниченный поиск улучшения, не доказательство глобального оптимума. Существенная экономия — от 5 минут или 1 км без увеличения времени, либо снижение риска.
- Время включает движение, ожидание открытия и serviceMinutes. Погрузка должна закончиться до windowTo. Конец — прибытие на склад с учётом времени открытия; разгрузка не включена. Для уже начатой точки пока закладывается полная длительность погрузки. Свободный текст warehouseHours не разбирается: диспетчер подтверждает соответствие структурированных окон графику, перерывам и выходным.
- Цвета: красный при рисках в текущем варианте, серый при неполной оценке, янтарный при улучшении без рисков, зелёный при соблюдённых окнах и отсутствии существенного улучшения. При недоступном участке вымышленные часы и экономия не показываются.
- Карта сравнивает дорожную геометрию 2ГИС (синий текущий / фиолетовый пунктир предложенный) на подложке OpenStreetMap; при отказе геометрии остаются списки. Геокодирование неоднозначного адреса или координаты далее 250 км от города дают просьбу уточнить данные.
- Перед применением сервер сверяет SHA-256 подпись версий маршрута, заданий, справочников и GPS для начатого рейса. Через 10 минут расчёт устаревает. Изменившиеся ресурсы, задания, GPS или порядок требуют новой проверки. Обычные ограничения reorder и подтверждение водителем сохраняются.

Документация интеграции: https://docs.2gis.com/en/api/navigation/routing/examples/routing и https://docs.2gis.com/en/api/navigation/routing/examples/types . Тестовые примеры работают с подставным провайдером; успешность доступа реального ключа и результаты на рабочих адресах проверяются отдельно на сервере.

### Место старта рейса
В форме маршрута диспетчер выбирает склад HAULZ или другой адрес (например, стоянку автомобиля). Выбор сохраняется в `snapshot.start`, переносится при публикации и отображается водителю. Новая миграция не нужна; старые маршруты начинаются со склада. Конечная точка остаётся складом HAULZ. Проверка запланированного маршрута учитывает сохранённый старт; адрес в окне проверки действует только на этот расчёт. После начала рейса используется достоверная GPS-позиция или явно обозначенный ориентир последней остановки, а не исходная стоянка.

### Мобильная навигация водителя
На мобильной ширине три раздела: «Главная» (день и назначенные рейсы), «Маршрут» (текущий шаг и раскрываемый список остановок), «Профиль» (данные водителя/авто, версия и обновление). Переключение вкладок не размонтирует рабочую форму и GPS. Обновление интерфейса блокируется при несохранённом вводе и очереди отметок; Android использует существующий манифест обновлений, веб — перезагрузку интерфейса по кнопке. Профиль не показывает внутренние адреса API. Цвета используют текущую тему, нижнее меню учитывает safe area телефона.

### Связь журнала счетов с перевозкой по заявке

Журнал сопоставляет номер заявки `pickup_jobs.data.zayavkaNumber` с `ZayavkaNumber` в сохранённой перевозке в рамках ИНН заказчика. Номер забора ещё не обязан быть передан в 1С. Места, вес, объём, платный вес и номер перевозки берутся из найденной перевозки; автоматическая сумма рассчитывается по этим данным. Ручная сумма остаётся ручной. Несколько совпадений, другой забор или конфликт номеров требуют сверки и блокируют передачу стоимости. Номер заявки отображается и при отсутствии перевозки.

Исправление требует обновления frontend и backend; новой миграции и изменения cron не требует. Перевозка с полем `ZayavkaNumber` должна присутствовать в кэше БД.
