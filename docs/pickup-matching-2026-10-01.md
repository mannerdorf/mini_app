# Сопоставление счетов и нескольких перевозок

Изменения от 01.10.2026, подготовлены локально.

- При найденном счёте остаётся кнопка со значком связи «Изменить сопоставление». Текущий документ выбран, если совпали номер и дата; замена использует проверяемый журнал счетов заказчика и текущую версию записи. История сопоставлений сохраняется. Запросы создания документов в 1С не выполняются при сопоставлении.
- К одному забору можно явно привязать 1–100 перевозок одного заказчика. Выбор сохраняется при поиске. Любой номер можно убрать, один из выбранных назначить перевозкой для счёта.
- cargoNumbers хранится в JSON данных забора; cargoNumber и zayavkaNumber остаются основной связью для существующего одиночного API 1С. Новая миграция не нужна. Общая стоимость относится к забору, отправляется один раз по выбранному основному номеру; на остальные номера не дублируется. Автоматическая отправка при нескольких перевозках блокируется; оператор проверяет сумму и нажимает выставление вручную.
- Места, вес, объём и платный вес суммируются. Отсутствующее значение не подменяется нулём. Журнал показывает все выбранные перевозки и заявки. Существующая синхронизация номера забора с заявкой 1С по-прежнему использует основную заявку; дополнительные связи сохраняются в HAULZ.
- Проверяется ИНН, уникальность номера во всём кэше, чужой номер забора, занятость в другом заборе и версия. Пересекающиеся ручные выборки сериализуются advisory locks в порядке номеров. После передачи стоимости состав перевозок по-прежнему нельзя менять; сопоставление самого счёта доступно.
- Получение счетов проверяет все выбранные перевозки. При разных найденных счетах требуется явное сопоставление. Повторная ручная отправка блокируется при известном счёте за забор на любой выбранной перевозке.

Проверки: frontend typecheck и production build прошли. Тесты UI и PGlite покрывают замену счёта, историю, выбор через поиск, основной номер, суммирование, удаление связи, устаревшие версии, чужого заказчика, занятый дополнительный номер, нормализованный кэш и существующие счета. В общем наборе первоначально упали два client.test.ts из-за старых mock-ответов с json() при использовании text(); фикстуры заменены на Response и проверены повторно.

В рабочую среду изменения не публиковались; реальных запросов создания счетов в 1С при проверках не было. При выпуске обновить backend перед frontend: старый backend не поддерживает transportNumbers. Учесть кеширование импортов Node при обновлении работающего API.
