# Этап 12 — защита настройки второго фактора

## Что закрыто локально

SEC-01: изменение настройки, выдача секрета Google, отключение и отвязка Telegram требуют короткой серверной сессии настройки. Эта сессия выдаётся после проверки пароля; при включённом MFA — также действующего второго фактора. Срок — пять минут, токен используется для одного изменения. Он хранится только в памяти компонента и не является токеном входа в приложение.

Чтение минимальных настроек для экрана входа/профиля требует первого фактора. Анонимный GET больше не работает. Клиент не трактует ошибку чтения как выключенный MFA.

Новый Google-секрет хранится отдельно до правильного кода. Подтверждение одновременно меняет настройки, потребляет сессию и фиксирует использование OTP. Неудачная или незавершённая настройка сохраняет действующий фактор. QR формируется локальной библиотекой qrcode; секрет больше не передаётся qrserver.com.

Изменения состояния и потребление кодов используют один Redis EVAL с проверкой ожидаемых значений. Коды Telegram разделены по назначению: вход, доступ к настройкам и подтверждение нового способа. Хранилище обязано различать отсутствующий ключ и сетевую ошибку; ошибки возвращают отказ, а не выключенный фактор. Ограничения попыток общие по аккаунту и IP.

Альтернативный endpoint telegram-unlink защищён той же сессией. Email-onboarding бота не может заменить активный Telegram-фактор другим чатом. Отвязка устаревшего чата не удаляет привязку другого чата.

## Обязательные условия выпуска

- Выпустить frontend, три API 2fa, telegram-unlink и tg-webhook вместе. Старые клиенты, отправляющие только login или изменяющие флаги напрямую, получат отказ. Не возвращать старый небезопасный fallback ради совместимости.
- Нужны рабочие PostgreSQL/лимиты этапа 10, Redis и разрешение Redis EVAL. Проверить это на тестовом контуре до production. В локальных тестах использовано изолированное атомарное хранилище и проверки адаптера; настоящие Redis/Telegram/1С не вызывались.
- Legacy-аккаунты подтверждаются существующим серверным механизмом проверки компаний в 1С. При недоступности этой проверки доступ к настройкам блокируется. Зарегистрированным аккаунтам нужен их личный пароль; системный пароль ADMIN_PASSWORD не является подтверждением личного второго фактора.
- Старый код записывал канонический login в нижнем регистре, а иногда дополнительный ключ исходного регистра. Перед выпуском нестандартных исторических инсталляций проверить наличие канонических записей; не удалять исходные ключи без сверки. Ошибка формата настройки блокирует изменение и требует поддержки.
- Проверить настройку Google от начала до конца, смену фактора Google ↔ Telegram, неправильный код, истечение пяти минут, повтор кода, отключение, отказ Redis и возврат в приложение на Android/iOS. Подтверждение кода и смена настроек не должны регистрироваться в логах с секретами/паролями.
- Если связь активного Telegram-фактора или Google-секрет уже потеряны, самостоятельное восстановление не должно отключать MFA по одному первому фактору. Нужна отдельная процедура поддержки; она этим изменением не создаётся.

## Что остаётся открытым

SEC-02: общие API всё ещё принимают login/password. Сессия настройки не устраняет обход клиентского MFA прямым вызовом защищённого API с первым фактором. Нужны серверные login challenges, полноценные сессии и их проверка во всех путях доступа, включая CMS/legacy/native.

SEC-06: существующие пароли аккаунтов всё ещё сохраняются в localStorage. Новая сессия настройки туда не записывается, но миграция общего входа и защищённого хранения ещё не выполнена.

Не объявлять приложение полностью защищённым MFA на основании закрытия одного SEC-01.
