## Продолжение: ошибки загрузки — 19 сентября 2026

**Исправлены выявленные сценарии UXA-18 и UXA-29. Итого локально реализован 21 из 29 пунктов; осталось 8.**

- UXA-18: техническое сообщение секционной границы ошибок больше не показывается открытым. Общий LoadError содержит понятное сообщение и закрытые сведения для поддержки; существующее обновление страницы и восстановление после обновления чанков сохранены.
- UXA-29: ошибка чтения списка возвратов отделена от ошибок обработки файлов. При сбое нет утверждения «Пока нет сохранённых обработок»; сохранённый предыдущий список помечается устаревшим. Повтор вызывает только refreshJobs.
- В Wildberries ошибка чтения содержит повтор loadData; вместо успешного пустого результата показано «Данные не загружены», число записей неизвестно. Во время загрузки счётчик также не выдаётся за подтверждённый ноль. Импорт/пересчёт не привязаны к новой кнопке повтора.

Проверки: 4 теста (LoadError, пустой/ошибочный список возвратов, существующий ErrorBoundary), сборка esbuild, браузерные ответы HTTP 503 с повтором чтения. Доказательства: [возвраты](ux-audit-assets/stage4-returns-error.json), [Wildberries](ux-audit-assets/stage4-wb-error.json). Frontend typecheck сохраняет 296 диагностик; ошибок в изменённых компонентах не добавилось.

Граница объёма: исправлена загрузка основных списков. Отдельные ошибки вложенных таблиц WB и интеграционные проверки реального сервера требуют дальнейшего внимания; этот этап не является аудитом всех запросов внутри WB. Сбой рендера раздела по-прежнему восстанавливается обновлением страницы; новые кнопки повторной загрузки списков выполняют только чтение.

## Продолжение: история и причины отсутствия счёта — 19 сентября 2026

**UXA-26 реализован; UXA-22 выполнен частично. Итого 22 пункта реализованы локально, 7 остаются открытыми (включая UXA-22).**

- История и последние изменения маршрута используют русские названия действий. Текущие русские сообщения API сохранены, известные старые коды переведены, неизвестный код отображается как «Другое действие». Исходный код доступен в раскрываемых технических сведениях истории.
- Перед редактором расчётов показано, почему забор не включён в счета: выключенное выставление либо ещё не выполненная сдача на склад. Для включённого забора указан день журнала и необходимость проверки перевозки/суммы там. Проверка использует общий pickupJobOnBillingTab, совпадающий с отбором backend.
- Остаток UXA-22: адресная диагностика найденной перевозки, расчётной суммы и очереди синхронизации номера непосредственно в карточке. Наличие номера заявки не объявляется подтверждением передачи в 1С.

Проверка: 4 теста объяснений/названий/редактора расчётов прошли; браузерный компонентный стенд собран esbuild; git diff --check пройден. Нового визуального прогона карточки и проверки с диспетчером в этом шаге не было. Миграции и серверные изменения не требуются.

Остаток: UXA-20–25, UXA-28. Коммит и push не выполнялись.

## Порядок работ

**Сначала сохранность ввода и достоверность информации → затем общие контракты UI → потом сложные сценарии → визуальная унификация → полная проверка ролей и устройств.**

Новый стиль не должен менять бизнес-правила незаметно. Не возвращать запрет удаления активных маршрутов, обязательные часы смен/доступности, удалённые карты и поля. Сохранение расчётов не отправляет стоимость в 1С; передача требует решения диспетчера.

### Оценки

- **S:** локальное изменение, обычно до одного рабочего дня с адресной проверкой.
- **M:** 2–4 дня, несколько компонентов или состояние формы/контракт API.
- **L:** от 5 дней, несколько подсистем, сложное восстановление/оффлайн или миграция дизайн-системы.

Это относительные оценки одного исполнителя, не календарная смета. В них нет ожидания доступа к стенду/устройствам. Общие компоненты сокращают повторную работу; нельзя просто складывать оценки всех находок. Для API/данных сначала проверить актуальную ветку и контракт.

## Этап 1. Сохранность ввода и достоверные результаты

**Объём:** первые 10 задач; ориентир L как единый этап, разбить на небольшие проверяемые изменения.

### 1A. Состояние формы

Компоненты: `PickupBillingTab`, `PickupDayRow`, `PickupJobBillingEditor`, `PickupJobOrderEditor`, `DocumentsOrderForm`.

**Риски:** старое значение перезапишет новое; бесконечные предупреждения при пустой форме; черновик чужого аккаунта; сохранение blob без политики очистки.

**Приёмка:** 0 потерянных dirty-полей в матрице двух строк, закрытия, polling, 409, смены компании. Нет предупреждения для неизменённой формы. Не успешное сохранение оставляет ввод.

### 1B. Истина в сообщениях

Компоненты: dashboard hooks/monitor, expenses list, order summary/success, billing editor.

- Финансовый вывод разрешён только после успешного ответа конкретного запроса, с периодом/датой данных.
- Ошибка не отображается как пусто или достоверный ноль.
- Тексты «Оформить» и номера соответствуют `order-submit`.
- API-ограничение редактирования отражается в UI до ввода; UI не заменяет серверную проверку.

**Приёмка:** во всех тестовых ошибках нет утверждений «все оплачено», «нет заявок» или «ручное выставление», если не было соответствующего результата.

- Все новые стили пилотных компонентов используют утверждённые семантические токены; исключения перечислены.
- Обычный текст ≥4.5:1, крупный ≥3:1; фокус видим и не обрезан.
- Проектная touch-цель 44–48 px для главных мобильных действий; плотный desktop — отдельный вариант.
- Нет глобального горизонтального скролла на 390/768/1440; внутренний скролл таблицы понятен и не скрывает идентификатор строки.
- При reduced-motion нет перемещения индикаторов/плавного скролла, задерживающего использование.
- На согласованном desktop-прототипе плана дня видны минимум три типовые рабочие строки без первой прокрутки.
- Анимация/новые компоненты не увеличивают бюджет загрузки без измерения и явного решения по TECH-04.

## Быстрые изменения с небольшим риском

Можно делать небольшими отдельными пакетами после baseline:

- UXA-08/09: корректные тексты и required номера; не менять алгоритм 1С.
- UXA-07: локальные theme-safe цвета таблицы; не весь дизайн сразу.
- UXA-06/29: явно отобразить ошибку чтения; не автоматизировать повтор записи.
- UXA-15: доступные имена уже существующих контролов.
- UXA-27/26: нулевой поиск и словарь событий.
- UXA-13: изоляция контекста диагностики.

UXA-01/02/03 не считать «простым косметическим исправлением»: они требуют проверки конфликтов и сохранности ввода. Новая общая форма или тема также требует регрессии потребителей.

## Этап 5. Финальная проверка и выпуск

**Объём:** M плюс существующие TECH-01/03/04 и аппаратные проверки. Не закрывать их только результатами компонентного стенда.

### Обязательные регрессионные сценарии

1. Две суммы изменены → сохранена одна → вторая и выделение остаются.
2. Карточка с новым номером → Escape/backdrop/закрыть → ввод защищён.
3. Во время ввода приходит новая версия → никакого молчаливого сброса/перезаписи.
4. Новая заявка → назад/смена раздела → черновик восстановим в правильной компании.
5. 503 в долгах/расходах/WB/возвратах → ошибка, не «всё оплачено/пусто».
6. Профиль/таблицы/админка → все основные действия доступны клавиатуре.
7. Тёмная финансовая таблица → заголовки, суммы, статусы, hover читаемы.
8. Заявка создаётся по описанному контракту, постоянный номер защищает повтор — API-03.
9. Передача партии → прогресс и неизвестный результат; подтверждённые строки повторно не отправляются.
10. Водитель → две точки без устойчивой сети → фото/места/заявка/очередь сохраняются; PICK-03/05.
11. Сдача с пустым номером запрещена и клиентом, и сервером; с номером проходит.
12. Забор без включённого счёта объясняет отсутствие в журнале; включённый попадает при выполнении остальных условий.
13. Удаление маршрута на любом этапе остаётся разрешённым по принятому требованию, с корректным предупреждением и согласованным состоянием водителя.
14. Полный App с нижней панелью и клавиатурой не перекрывает последнее поле/действие.
15. Смена компании, выход и снятие роли не показывают чужие черновики/данные — SEC-03/04/06/08.

### Условия завершения

- Все 29 ID имеют статус: исправлено и проверено / подтверждённый остаток / гипотеза отклонена с доказательством / согласованно отложено. «Не воспроизвелось» без условий не равно исправлению.
- В исправленном объёме нет открытых P0/P1 и потерянного ввода; существующие P0 из `todo.md` решаются отдельно как условия общего выпуска.
- Критичные сценарии пройдены в обеих темах и на реальных устройствах; недоступные проверки перечислены явно.
- Для каждого принятого исправления есть before/after, адресная проверка и обновлённые ссылки на код.
- Коммит, push, миграции и deployment выполняются только в задаче реализации с соответствующим разрешением. Этот аудит их не выполняет.
