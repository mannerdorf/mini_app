# Очередь плановой даты прибытия

## Поведение

`POST /api/sendings-plan-date` сохраняет до 500 перевозок в `plan_date_queue` и отвечает 202.
В 1С из пользовательского запроса ничего не отправляется. Требуются учётные данные
зарегистрированного пользователя с правом `eor` или `supervisor`, либо проверенный super-admin token.
Пароли и токены не сохраняются в очереди.

Одна строка на перевозку. Повтор той же даты возвращает существующий результат.
Ожидающую дату можно заменить. Если предыдущая запись отправляется или её результат
неизвестен, новая дата блокируется. После `done`/`error` разрешена другая дата.
Повтор ошибочной записи той же даты автоматически не выполняется.

`/api/cron/process-plan-date-queue` обрабатывает одну перевозку за запуск под advisory lock.
Он использует общую очередь доступа к 1С и ограничение 25 секунд на сетевую операцию.
При ошибке конфигурации задания остаются в очереди.

- `pending` — в очереди;
- `sending` — запрос записи начат;
- `verifying` — только чтение Getperevozka после потери ответа;
- `done` — явный Success=true либо прочитана совпадающая плановая дата;
- `uncertain` — три чтения не дали подтверждения, нужна ручная сверка;
- `error` — явный отказ 1С.

После сбоя процесса `sending` старше 3 минут переводится в проверку, не в повтор записи.
Для сверки используются только явные поля плановой даты и совпадающий номер перевозки.
Фактическая дата прибытия, дата из кэша или ответ без номера не подтверждают запись.
Если продуктивный Getperevozka не возвращает эти поля, результат останется «Требует сверки».
Это необходимо проверить на реальном ответе после развёртывания; API 1С не изменяется.

После подтверждения обновляются поля плановой даты в нормализованном и старом кэше,
без изменения времени свежести всего снимка. Push отправляется best-effort после подтверждения.
Интерфейс читает последние 100 заданий каждые 10 секунд только на видимой странице.

## Развёртывание

Сначала коммит/пуш кода, затем обновить checkout на API и cron VPS.
Применить миграцию **один раз** к общей БД:

```bash
cd /opt/haulz/app
(
  set -e
  set -a
  source /opt/haulz/.env
  set +a
  psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f migrations/120_plan_date_queue.sql
)
```

Перезапустить `haulz-api` на API VPS и `haulz-cron` на cron VPS. Развернуть фронтенд
вместе с API: старый клиент не передаёт авторизацию и не умеет показывать очередь.
На cron VPS добавить в существующий crontab (не заменять остальные строки):

```cron
* * * * * /opt/haulz/cron-call.sh /api/cron/process-plan-date-queue
```

Учётные данные 1С: PLAN_DATE_SERVICE_LOGIN/PASSWORD, либо HAULZ_1C_SERVICE_LOGIN/PASSWORD,
либо PEREVOZKI_SERVICE_LOGIN/PASSWORD. Проверять наличие, не печатать значения.

Ручной запуск обработчика действительно отправляет ожидающее задание в 1С:

```bash
/opt/haulz/cron-call.sh /api/cron/process-plan-date-queue
```

Проверка БД: `SELECT cargo_number,target_date,state,attempts,checks,last_error FROM plan_date_queue ORDER BY updated_at DESC;`
При `uncertain` не сбрасывать состояние в pending без сверки с 1С.
