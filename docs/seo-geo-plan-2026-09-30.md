# HAULZ: план SEO и GEO

Дата исследования: 30.09.2026. План, без изменений работающего сайта.

Расширенная программа с отдельными направлениями SEO, AEO, GEO, приоритетом B2B и двумя стадиями автономного контент-завода: [план реализации](seo-aeo-geo-content-factory-2026-09-30.md). Этот документ сохраняется как исходный аудит.

## 1. Цель и границы

Получать целевые заявки на перевозки Москва ↔ Калининград из Яндекса, Google и ответов Алисы, ChatGPT, Perplexity, Copilot. GEO здесь — Generative Engine Optimization: доступность и полезность материалов для генеративного поиска. Региональное продвижение Москвы/Московской области и Калининграда — отдельная, связанная задача.

Изучены исходный код публичных экранов, маршрутизация, генерация HTML, canonical, robots, обе карты сайта, блог и фактические HTTP-ответы трёх доменов. Снимок: `audits/seo-live-2026-09-30.json` (поле bytes в нём — длина декодированного текста, не размер сетевой передачи).

Не проверены закрытые отчёты Вебмастера, Метрики, Search Console и Bing, реальный охват индекса, позиции, конверсии, карточки организаций и полевые Core Web Vitals. Данных для обещания трафика или сроков попадания в топ нет. Ошибка открытия сайта веб-инструментом не означает блокировку роботов: прямые HTTP-проверки доступны.

## 3. Подтверждённые проблемы и исправления

### P0 — единый адрес сайта

Все три HTTPS-корня `.space`, `.pro`, `.ru` отвечают `200` без перехода на основной домен. Canonical в коде и карты сайта ориентированы на `.space`, но в первоначальном HTML главной canonical отсутствует.

**Решение:** предварительно оставить `.space` основным, так как он уже заложен в коде. До окончательного выбора сравнить историю доменов, ссылки и трафик в кабинетах. Не переносить сайт на `.ru` только ради расширения домена. Для дублей публичных страниц — постоянные перенаправления с сохранением пути; синхронизировать canonical, sitemap, внутренние ссылки и разметку. API, вход, deep links мини-приложений и интеграции проверять отдельно, не перенаправлять весь домен вслепую.

**Приёмка:** каждая публичная страница имеет единственный конечный URL; остальные варианты переходят за один шаг. Проверены HTTPS/www/завершающий слеш. Сейчас страница направления открывается со слешем, а canonical и sitemap указывают вариант без него — устранить расхождение.

### P0 — индексируемый HTML

Главная, калькулятор, FAQ, склады, компания и блог возвращают одинаковую оболочку с общим title, без H1 и canonical в исходном ответе. Метаданные добавляет `useGuestDocumentMeta` после запуска JS. Это не доказывает отсутствие индексации, но создаёт зависимость от рендеринга.

**Решение:** отдавать публичные страницы готовым HTML через SSG/SSR; интерактивный калькулятор подключать поверх. Не требуется переписывать рабочий кабинет. Использовать общий источник контента для React и HTML: генератор `scripts/generate-route-seo-html.mjs` сейчас содержит собственные сокращённые тексты. Одинаковое содержание для людей и роботов, без подмены по User-Agent.

**Приёмка:** без JavaScript читаются H1, описание услуги, ответы, контакты и ссылки; присутствуют уникальные title/description/canonical и JSON-LD. Статическая и интерактивная версии совпадают по фактам.

### P0 — настоящая страница 404

Проверенный несуществующий адрес `/seo-audit-missing-page-20260930` отдаёт `200` с оболочкой главной; `parseGuestRoute` для неизвестного пути выбирает home.

**Решение:** неизвестные публичные URL и несуществующие статьи возвращают HTTP 404, понятный экран и полезные ссылки. Известные маршруты приложения продолжают открываться напрямую.

### P1 — sitemap и блог

Статическая карта содержит 10 адресов, API-карта — 8. В статической есть два параметризованных калькулятора. На момент проверки API-карта не содержала статей; код ограничивает выборку 100 публикациями и при ошибке БД молча отдаёт статический список.

**Решение:** единая генерация карты или согласованный sitemap index; только канонические URL с `200`. Для калькуляторов выбрать политику: единая страница либо полноценные отдельные страницы направлений — не три одинаковых страницы. Добавить достоверный lastmod, пагинацию при росте блога, наблюдение за ошибками генерации. Не менять lastmod каждый день без изменения материала.

У статьи брать title и description из CMS, выводить автора/эксперта, дату публикации и обновления, источники. Добавить Article/BlogPosting и BreadcrumbList. Существующее published_at загружается, но в просмотренном компоненте статьи не показывается. Навигацию между публичными страницами делать обычными `a href`, даже если переход перехватывает React: в текущих экранах часть переходов реализована только кнопками onClick.

### P1 — индексация и скорость

robots уже разрешает публичные страницы через `User-agent: *`; отсутствие отдельных имён ИИ-роботов само по себе не блокирует их. Закрытые разделы не должны попадать в sitemap. Для входа, восстановления и технических страниц выдавать noindex сервером; robots не заменяет авторизацию и не гарантирует удаления URL из индекса.

Измерить загрузку публичных страниц отдельно от кабинета: объём JS, изображения первого экрана, шрифты, карты, задержку ответа. Убрать из первоначального публичного пакета библиотеки отчётов, PDF, рабочих таблиц и кабинета, если анализ сборки подтвердит их загрузку. Не объявлять сайт медленным без измерения. Метрики собирать на мобильных устройствах и реальных посетителях.

## 4. Предлагаемая структура публичного сайта

Сохранить существующие полезные URL. Новые ниже — предложения, не существующие страницы:

- `/` — кто такие HAULZ, направления, услуги, доказательства, расчёт и заявка.
- Два существующих маршрута — основные коммерческие страницы.
- `/uslugi/sbornye-gruzy` — сборные грузы и платный вес.
- `/uslugi/perevozka-paromom` — условия паромной доставки.
- `/uslugi/avtoperevozki` — автомобильная доставка и ограничения.
- `/uslugi/zabor-gruza` — забор, МКАД/КАД, погрузка, расчёт доплат.
- `/uslugi/dostavka-do-adresa` — последняя миля.
- `/uslugi/upakovka` — коробки, паллеты, жёсткая упаковка.
- `/sklady` + `/sklady/moskva`, `/sklady/kaliningrad` — реальные терминалы, адрес, проезд, часы, ограничения приёмки.
- `/tarify` — объяснение тарифа, дата действия, примеры и переход к калькулятору.
- `/faq`, `/blog`, `/o-kompanii`, `/kontakty`, `/cases` — ответы и подтверждение опыта.

Создавать только страницы реально оказываемых услуг с различающимся содержанием. Не генерировать сотни городов или комбинаций весов, где нет собственной услуги/информации. Таможню и отдельные классы грузов выделять только после подтверждения возможностей компании.

### Шаблон коммерческой страницы

1. Прямой ответ: что перевозим, откуда/куда, для кого.
2. Условия и сроки с оговорками и датой актуальности; без выдуманных гарантий.
3. Примеры стоимости из действующего калькулятора: вес, объём, платный вес, способ перевозки, забор/доставка, доплаты, НДС, дата расчёта. Обновлять при изменении тарифной версии.
4. Адреса терминалов, график и правила приёмки.
5. Документы, ограничения и упаковка.
6. Реальный обезличенный кейс с разрешением на публикацию.
7. Ответы на вопросы конкретного маршрута и ссылка на заявку.

Не переносить сумму только за забор в пример полной перевозки. Тарифные данные брать из общей версии тарифов, а не копировать вручную в маркетинговые страницы.

## 5. GEO: как сделать HAULZ удобным источником ответов

Каждая страница должна содержать краткий самостоятельный ответ перед подробностями. Например: «Как считается доплата за МКАД?» — объяснение по участкам, единицы измерения, актуальная таблица и пример расчёта. Указанные в текущем FAQ ответы «зависит от режима, смотрите калькулятор» дополнить конкретными условиями, а не придуманными сроками.

Начальные темы материалов:

| Вопрос | Целевая страница |
|---|---|
| Сколько стоит отправить паллету Москва — Калининград? | Маршрут + пример расчёта |
| Что входит в стоимость перевозки? | Тарифы |
| Когда выбирать паром, а когда авто? | Сравнение подтверждённых способов доставки |
| Как рассчитывают объёмный/платный вес? | Сборные грузы + калькулятор |
| Как считают километры за МКАД и КАД? | Забор груза |
| Какие документы нужны на груз? | FAQ / экспертная статья |
| Как отправить груз обратно из Калининграда? | Обратный маршрут |
| Какая упаковка нужна для хрупкого груза? | Упаковка |
| Где сдать груз в Москве и Калининграде? | Страницы складов |
| Как бизнесу получать счета и документы? | Публичная справка о сервисе |

Разметка: Organization с постоянным @id, Service, BreadcrumbList, Article и подходящая разметка реальных филиалов. Факты в JSON-LD должны присутствовать на странице. FAQPage не считать гарантией расширенного сниппета или цитирования.

Подкреплять бренд независимыми подтверждениями: реальные карточки организации, отраслевые публикации, партнёрские упоминания, кейсы клиентов, настоящие отзывы. Единообразно использовать HAULZ/ХОЛЗ, юридическое название, адреса и телефоны. Не покупать фиктивные рейтинги и не публиковать автоматически созданные «обзоры лучших компаний» от лица независимых авторов.

## 6. Поисковые системы и ИИ

- **Яндекс / Алиса:** Вебмастер, индексация приоритетных URL, проверка региона, карта сайта, релевантные коммерческие страницы. Отчёт «Видимость сайта в Алисе AI» показывает упоминания и примеры запросов; данных может быть недостаточно. [Яндекс](https://yandex.ru/support/webmaster/ru/service/alice-answers).
- **Региональный поиск:** проверить карточки реальных складов в Яндекс Бизнесе и согласованность с сайтом, добавить фотографии въезда, схему проезда и действующие часы. Создавать только реальные филиалы. [Яндекс Бизнес](https://yandex.ru/support/business-priority/ru/branches/branches-manual).
- **ChatGPT Search:** доступ для OAI-SearchBot; GPTBot относится к обучению и управляется отдельно. Разрешение GPTBot не является условием появления в поисковых ответах. Проверить WAF и официальные IP, а не только строку User-Agent. [OpenAI](https://developers.openai.com/api/docs/bots).
- **Perplexity:** доступ для PerplexityBot и корректная работа запросов пользователей Perplexity-User; сверять официальные IP. [Perplexity](https://docs.perplexity.ai/docs/resources/perplexity-crawlers).
- **Google AI / Gemini:** обычные требования SEO остаются основой для AI-функций Google Search; отдельная «магическая» AI-разметка не нужна. Это не гарантия присутствия во всех ответах отдельного приложения Gemini. [Google](https://developers.google.com/search/docs/appearance/ai-features).
- **Bing / Copilot:** подключить Bing Webmaster Tools и смотреть AI Performance, если отчёт доступен. [Bing](https://www.bing.com/webmasters/help/ai-performance-9f8e7d6c).

`llms.txt` — необязательный эксперимент после основных работ, а не приоритет и не гарантия индексации. Доступный API калькулятора полезен для интеграций, но не заменяет HTML-страницы. Публикация данных не гарантирует рекомендацию модели.

## 7. План на 90 дней

Оценки — порядок величины для планирования, не обещание результата; зависят от доступа к аналитике и готовности контента.

| Период | Работа | Ответственный | Критерий готовности |
|---|---|---|---|
| Дни 1–3 | Кабинеты, базовые метрики, выбор основного домена, матрица URL | SEO + владелец | Зафиксированы основной домен, коммерческие цели и стартовые данные |
| Недели 1–2 | Готовый HTML, canonical/редиректы, 404, robots/sitemap | Разработчик | Все приоритетные страницы читаются без JS; технические проверки проходят |
| Недели 2–3 | Блог: метаданные, даты, авторы, разметка; crawlable-навигация | Разработчик + редактор | Публикация автоматически обновляет HTML и sitemap; нет общего title |
| Недели 3–4 | Два направления, тарифы, склады, компания | Логист + редактор + SEO | Проверенные факты, примеры цен, понятная заявка, адреса и документы |
| Недели 5–8 | 4–6 страниц услуг и 6–8 экспертных материалов | Редактор + эксперт | Каждый материал закрывает отдельную потребность и связан с услугой |
| Недели 6–12 | Карточки филиалов, кейсы, отраслевые упоминания, улучшения по данным | Маркетолог + владелец | Реальные профили, подтверждения и измеримые изменения трафика/заявок |
| Каждую неделю | Индексация, ошибки, конверсии, источники в ИИ | SEO + аналитик | Отчёт по фиксированному набору страниц и запросов |

Сначала техника и две главные коммерческие страницы. Массовую публикацию статей до исправления HTML и доменов не запускать.

## 8. Как измерять результат

Основные бизнес-метрики: квалифицированные заявки из органики, заявки после расчёта, стоимость привлечения, доля дошедших до перевозки. Разделять брендовые и небрендовые запросы, города, направления и новые/повторные обращения.

События: начало и завершение расчёта, отправка заявки, клик по телефону/мессенджеру, обращение со страницы склада. Реализацию и текущую доступность Метрики/согласий проверить отдельно; наличие событий не установлено этим аудитом.

Технические цели: 100% приоритетных URL доступны и имеют корректные канонические адреса, отсутствие soft-404 на проверенном наборе, основной контент в HTML, все опубликованные индексируемые статьи присутствуют в sitemap. Индексирование контролируется отдельно — техническая готовность не равна включению в индекс.

Для GEO — фиксированный набор 30–50 вопросов по направлениям, цене, документам, терминалам и упаковке. Раз в неделю фиксировать сервис, дату, формулировку, режим поиска и цитируемый URL. Различать упоминание бренда и реальную ссылку. Не выводить рыночную долю из нескольких ручных запросов. Учитывать вариативность ответов; использовать официальные отчёты и реферальные переходы как дополнительные источники.

## 9. Что требуется от владельца перед реализацией

1. Доступы к отчётам Яндекс Вебмастера/Метрики, Google Search Console, Bing Webmaster Tools — через разрешения, не передачу паролей.
2. Подтверждение приоритетного домена на основании его истории и показателей.
3. Утверждённые условия услуг, сроки, адреса, графики, реквизиты, правила публикации тарифов и кейсов.
4. Выбор приоритетной аудитории: новые B2B-клиенты и направления/услуги с наиболее ценными заявками.

До получения этих данных можно делать технические исправления, не требующие миграции домена, и проектировать шаблоны. Перенос домена, изменение публичных тарифов и обещаний клиентам требует отдельного решения владельца.
