# Этап 11: изменения и выпуск

**Уточнение 18.09.2026:** прежний запрет удаления выполняемого маршрута отменён по решению пользователя. В актуальном коде диспетчер удаляет маршрут любого статуса; заборы, фотографии и история сохраняются.

Локальные изменения от 17.09.2026. Это не подтверждение готовности всего TODO или production-развёртывания.

## Порядок выпуска

1. Выполнить требования этапа 10 (миграция 111 и доверенные proxy для лимитов).
2. Применить `112_one_c_submissions.sql` **до** кода отправки заявок. Без таблицы отправка закрывается с 503. Миграция не выполняет внешних запросов и не исправляет старые дубли.
3. Применить `113_pickup_location_retention.sql` для индекса очистки GPS. На большой рабочей таблице оценить блокировку CREATE INDEX; миграция локально проверена, рабочая база не использовалась.
4. Выпустить backend и frontend согласованно. Не удалять таблицу квитанций при откате: она предотвращает повторные отправки.
5. Проверить на тестовом контуре отправку, обрыв после внешнего успеха и повтор. Не проверять это созданием повторной рабочей заявки.

## Отправка в 1С

Общая отправка захватывает уникальную операцию по ИНН заказчика и неизменному номеру заявки клиента. Хеш содержимого защищает от повторного использования номера с изменёнными данными. Одновременный повтор блокируется, успешный повтор возвращает сохранённую квитанцию. В БД не сохраняются заголовки авторизации внешнего запроса.

`Idempotency-Key` передаётся в 1С, но поддержка заголовка провайдером **не подтверждена**. Локальная защита не зависит от его поддержки.

`uncertain` и зависшее `sending` нельзя автоматически очищать по таймеру. Оператор должен найти заявку в 1С по исходному номеру клиента, сверить заказчика и состав и сохранить подтверждённый результат. Пока не согласован API сверки и не сделан интерфейс оператора, такие операции требуют поддержки. **Не создавать новый номер и не удалять запись, чтобы обойти блокировку.** API-03 остаётся частичным.

## Отмена запросов

На локальном Node-сервере timeout/отключение клиента передаёт AbortSignal в 2ГИС и отправку заявки в 1С. Поздний ответ защищён от повторного завершения HTTP. Уже выполненное действие внешнего сервиса не откатывается отменой соединения. Остальные внешние вызовы, serverless-платформа и полноценное получение статуса требуют продолжения API-06.

## Данные водителя

- Снимки IndexedDB старше семи суток истекают при чтении. Старые записи без известного времени снимка тоже не используются.
- Неотправленные фото/очередь не удаляются автоматически. Черновики старше 30 суток либо без даты требуют внимания водителя; возраст не означает автоматическое удаление.
- Выход/удаление аккаунта проверяет сохранённую работу; отмена оставляет пользователя в приложении. Ошибка хранилища отменяет очистку. Подтверждённый выход удаляет принадлежащие логинам записи.
- Запись кэша закрывающегося аккаунта блокируется. Межвкладочная синхронизация очистки, квоты и выгрузка приложения ОС ещё требуют проверки/доработки; SEC-08/PICK-03 не закрыты.
- GPS старше семи суток с последнего наблюдения скрыт из выдачи. Очистка выполняется порциями до 100 строк при чтении снимка. При отсутствии обращений строки физически остаются в базе: для гарантированного срока нужен плановый cleanup, а не только обработчик чтения.
- Фоновый GPS не реализован. Монитор явно объясняет, что при сворачивании приложения показывает последнее принятое положение с возрастом.

## Сборка

`npm run check:bundle` после `npm run build` проверяет статический граф `index.html` по манифесту Vite: не более 750000 байт JS / 225000 байт gzip. Графики, PDF, Excel, Firebase и страница возвратов не допускаются в стартовом графе. CSS, изображения, загрузки после действий и реальное время отрисовки этим бюджетом не измеряются.

`npm run typecheck:frontend` включает строгую проверку всего src. Пока она не проходит, frontend не объявляется типобезопасным и этот пункт остаётся открытым. Не заменять это ослаблением strict или исключением проблемных компонентов.
